3장. 요구사항 분석과 데이터 모델링이란?

1. 요구사항에서 데이터 찾기

1.1 화면·기능 명세·업무 문장 함께 읽기

요구사항 분석(requirements analysis)은 서비스가 해야 할 일과 지켜야 할 조건을 확인하는 과정입니다. 데이터베이스를 설계할 때는 요구사항에서 관리할 데이터와 데이터에 적용할 규칙을 찾습니다.

화면에는 사용자가 입력하거나 조회하는 정보가 나타납니다. 기능 명세에는 버튼을 눌렀을 때 일어나는 동작이 적혀 있습니다. 업무 문장에는 화면만으로 알기 어려운 운영 조건이 담깁니다. 세 자료를 함께 읽어야 필요한 데이터를 빠뜨리지 않습니다.

주문 서비스를 예로 들겠습니다. 주문 화면에는 상품명, 수량, 받는 사람, 배송지가 보입니다. 하지만 화면만 보고는 주문한 회원과 주문 접수 시각을 언제 기록해야 하는지 알 수 없습니다.

자료확인한 내용설계할 때 적을 내용
주문 화면수량과 받는 사람, 배송지를 입력한다.주문 수량, 수령인명, 주문 배송지
주문 기능 명세로그인한 회원이 주문을 확정한다.주문 회원, 주문 접수 시각
주문 상세 화면주문번호, 상품명, 적용 단가, 주문 상태를 보여 준다.주문번호, 주문한 상품, 주문 당시 적용 단가, 주문 상태
업무 문장상품 가격이 바뀌어도 접수된 주문 금액은 바뀌지 않는다.현재 판매 단가와 주문 당시 적용 단가를 구분
업무 문장한 주문에는 여러 상품을 담을 수 있다.주문 전체 정보와 주문 항목별 정보를 구분

화면의 항목 이름만 옮기면 마지막 두 조건을 놓치기 쉽습니다. 같은 ‘가격’이라도 현재 판매 가격인지, 주문에 적용한 가격인지에 따라 의미가 다릅니다.

기능을 읽을 때는 “무엇을 입력하는가”에 이어 “나중에 무엇을 다시 알아야 하는가”를 확인합니다. 주문 당시 배송지를 다시 보여 주어야 한다면, 회원이 현재 등록한 주소만으로 충분한지 검토해야 합니다.

화면의 모든 동작을 데이터로 저장해야 하는 것은 아닙니다. 주문 상세 영역을 접고 펼치는 동작은 화면 기능입니다. 접힌 상태를 다음 접속에도 유지한다는 요구가 없다면, 그 상태를 데이터베이스에 보관할 이유는 없습니다.

요구사항마다 번호를 붙이면 설계 근거를 찾기 편합니다. 예를 들어 ‘R01 주문 접수’, ‘R02 주문 상세 조회’처럼 적습니다. 이후 데이터 항목 옆에 요구사항 번호를 남기면, 어떤 기능 때문에 필요한 항목인지 추적할 수 있습니다.

1.2 입력 데이터·시스템 기록·계산 결과 구분

필요한 정보는 사용자가 입력한 값에만 한정되지 않습니다. 시스템이 기록하는 값과 다른 데이터로 계산하는 값도 함께 찾아야 합니다.

구분뜻주문 서비스의 사례
입력 데이터사용자나 관리자가 직접 제공하는 값주문 수량, 수령인명, 배송지
시스템 기록업무 동작에 따라 시스템이 정하거나 남기는 값주문번호, 주문 회원, 주문 접수 시각
계산 결과다른 값을 이용해 구하는 값항목 금액, 주문 상품 금액 합계

주문 회원은 로그인한 회원 정보에서 가져올 수 있습니다. 주문 접수 시각은 주문을 접수할 때 시스템이 기록합니다. 입력란이 없어도 주문을 다시 조회하려면 필요한 정보입니다.

계산 결과는 어떤 원본 데이터로 구하는지 적어 둡니다. 이 장의 사례에서 항목 금액은 ‘주문 당시 적용 단가 × 주문 수량’입니다. 주문 상품 금액 합계는 해당 주문의 항목 금액을 모두 더한 값입니다. 배송비와 할인은 이 계산에 포함하지 않는다고 정합니다.

예를 들어 적용 단가가 12,000원이고 수량이 2개라면 항목 금액은 24,000원입니다. 현재 상품 가격이 13,000원으로 바뀌더라도, 이미 접수한 주문의 항목 금액은 그대로여야 합니다. 따라서 계산식과 함께 계산에 사용할 값의 기준도 명확해야 합니다.

계산할 수 있다는 이유만으로 저장 여부를 바로 결정하지는 않습니다. 원본 데이터로 다시 계산할 수 있는지, 확정된 결과를 별도로 남겨야 하는지 확인해야 합니다. 이 단계에서는 필요한 정보와 계산 근거를 기록합니다.

2. 업무 규칙 명세

2.1 유일성·필수성·수량·보관 기간

업무 규칙(business rule)은 서비스에서 허용하거나 금지하는 조건입니다. “주문을 저장한다”는 문장만으로는 충분하지 않습니다. 어떤 주문을 정상 데이터로 인정할지까지 정해야 합니다.

다음은 주문 서비스에서 확인할 규칙입니다. 각 조건은 모든 서비스에 적용하는 정답이 아닙니다. 요구사항으로 합의해야 할 내용입니다.

구분확인할 질문명확하게 적은 규칙의 사례
유일성어떤 범위에서 같은 값이 중복되면 안 되는가?주문번호는 전체 주문에서 중복되지 않는다.
필수성언제 반드시 값이 있어야 하는가?주문 접수 시 수령인명과 배송지가 있어야 한다.
수량몇 개까지 허용하는가?접수된 주문에는 주문 항목이 1개 이상 있어야 한다.
값의 범위어떤 값을 허용하는가?주문 수량은 1 이상인 정수여야 한다.
보관 기간언제부터 얼마나 보관하는가?보관 대상, 기산 시점, 기간, 만료 후 조치를 정한다.

유일성에는 적용 범위가 필요합니다. “순번은 중복될 수 없다”보다 “같은 주문 안에서 항목 순번은 중복될 수 없다”가 정확합니다. 다른 주문에서 같은 순번을 사용하는 것은 허용할 수 있기 때문입니다.

필수성에는 적용 시점도 필요합니다. 주문 접수 시 배송지는 필수여도, 아직 입력 중인 주문에는 없을 수 있습니다. 입력 중인 주문까지 저장하는 서비스인지에 따라 규칙이 달라집니다.

수량을 읽을 때는 속성 값의 크기와 연결된 대상의 개수를 구분합니다. ‘주문 수량은 1 이상’은 속성 값의 조건입니다. ‘주문에는 항목이 1개 이상’은 주문에 속한 대상의 개수에 관한 조건입니다.

보관 기간은 “오래된 주문은 삭제한다”처럼 적지 않습니다. 예를 들어 교육용 정책을 ‘배송 완료일로부터 24개월 보관’으로 정했다고 가정하겠습니다. 이때는 배송이 끝나지 않은 주문과 취소 주문의 보관 기준도 확인해야 합니다. 실제 운영에 적용할 보관 기간은 관련 요구와 정책을 확인해 별도로 확정합니다.

모호한 문장은 임의로 해석하지 않고 질문으로 바꿉니다. 답변을 받기 전의 가정과 확정된 규칙도 구분합니다.

원래 문장추가로 확인할 질문답에 따라 달라지는 설계

질문에는 왜 확인해야 하는지도 적습니다. “부분 취소가 가능한가?”라는 질문에 “부분 취소가 가능하면 항목별 취소 대상과 수량을 관리해야 한다”는 설명을 덧붙입니다. 그러면 검토자가 답변에 따라 설계가 어떻게 달라지는지 이해하기 쉽습니다.

확인 사항은 다음과 같이 관리할 수 있습니다.

‘확인 중’은 누락과 다릅니다. 질문과 설계에 미치는 영향을 남겨 두면, 설계를 마치기 위해 무엇을 결정해야 하는지 알 수 있습니다. 답변을 받으면 관련 요구사항과 데이터 정의도 함께 고칩니다.

3. 엔터티와 속성 도출

3.1 관리할 대상과 한 행의 의미

엔터티(entity)는 데이터를 모아 관리할 대상이나 사건의 유형입니다. 회원과 상품은 대상에 해당하고, 주문은 업무에서 발생한 사건에 해당합니다.

엔터티는 관계형 설계에서 보통 테이블로 표현합니다. 다만 이 단계에서는 테이블 생성문보다 “무엇을 관리하는가”와 “한 행이 무엇을 뜻하는가”를 먼저 정합니다.

요구사항에서 명사를 찾는 것은 출발점입니다. 모든 명사가 엔터티가 되지는 않습니다. 배송지는 주문의 속성일 수 있고, ‘주문 조회’는 기능 이름입니다. 배송지를 독립적으로 등록하고 관리하는 요구가 있다면 별도 대상으로 검토할 수 있습니다.

앞에서 정리한 주문 요구사항은 다음처럼 묶을 수 있습니다.

엔터티 후보한 행의 의미함께 관리할 속성의 사례
회원가입한 회원 한 명회원번호, 회원명
상품판매 관리 대상 상품 하나상품번호, 상품명, 현재 판매 단가
주문접수된 주문 한 건주문번호, 주문 회원, 접수 시각, 수령인명, 배송지
주문 항목한 주문에서 주문한 상품 한 종류주문, 상품, 주문 수량, 주문 당시 적용 단가

주문 항목의 정의에는 Q02의 답변이 반영되어 있습니다. 같은 주문에서 같은 상품을 다시 담으면 수량을 합치므로, 같은 상품을 별도 항목으로 반복하지 않습니다. 옵션이 다른 상품을 어떻게 구별할지는 이 사례의 범위에서 제외합니다.

한 행의 의미는 작은 데이터로 확인하면 분명해집니다. 주문 O3101에 머그컵 2개와 메모장 3개를 담았다고 가정하겠습니다.

이 표의 한 행은 주문 한 건이 아니라 주문 항목 하나입니다. 주문은 한 건이고 항목은 두 개입니다. 따라서 주문 건수와 주문 항목 수를 구분해서 셀 수 있어야 합니다.

한 행을 설명할 때 “주문 정보 하나”처럼 넓게 적으면 해석이 갈립니다. “접수된 주문 한 건”이나 “한 주문에서 주문한 상품 한 종류”처럼 범위를 밝혀야 합니다.

아직 아무도 주문하지 않은 상태, 주문에 여러 상품이 있는 상태도 검토합니다. 이런 상황을 표현하지 못한다면 엔터티의 범위나 한 행의 의미를 다시 확인해야 합니다.

3.2 속성의 의미·단위·허용값 정의

속성 이름만으로는 모두가 같은 뜻으로 이해하기 어렵습니다. ‘금액’에는 현재 판매 단가, 주문 당시 적용 단가, 항목 금액이 모두 포함될 수 있습니다. 이름과 함께 의미, 단위, 허용값을 정의해야 합니다.

여기서 작성하는 설계용 데이터 사전은 엔터티와 속성의 뜻, 적용 규칙을 정리한 문서입니다. 앞 장에서 조회한 Oracle 데이터 사전은 DBMS가 객체 정보를 관리하는 체계입니다. 이 장의 설계용 문서는 테이블을 만들기 전에도 작성할 수 있습니다.

위 표에서 ‘주문 당시 적용 단가’는 나중에 상품 가격이 바뀌어도 뜻이 달라지지 않습니다. 현재 판매 단가와 다른 사실을 기록하기 때문입니다. 0원 상품을 허용하지 않는 업무라면 허용값도 ‘0 초과인 정수’로 바꿔야 합니다.

시각을 정의할 때는 어떤 사건이 발생한 순간인지 적습니다. ‘주문 시각’이라는 이름보다 ‘접수 시각’이 기준을 분명하게 드러냅니다. 날짜만 필요한지, 시각까지 필요한지, 어느 시간대를 기준으로 하는지도 정의합니다.

값이 없을 수 있다면 그 이유를 적습니다. 배송 요청사항은 주문자가 적지 않을 수 있습니다. 반면 배송 완료 시각은 아직 배송이 끝나지 않았기 때문에 없을 수 있습니다. 두 항목은 값이 없는 업무상 이유가 다릅니다.

‘초안’이라는 표시는 어디까지 결정했는지 드러냅니다. 아직 확인하지 않은 할인이나 배송비를 계산식에 임의로 넣지 않습니다. 요구사항이 추가되면 계산 정의를 수정합니다.

이 단계에서는 Oracle 데이터 타입이나 인덱스를 정할 필요가 없습니다. 먼저 같은 속성을 누구나 같은 뜻으로 읽을 수 있게 만듭니다.

4. 연습문제 — 주문 서비스의 데이터 사전 작성

다음 요구사항을 읽고 설계용 데이터 사전 초안을 작성합니다. 테이블 생성문과 ERD는 작성하지 않습니다.

요구사항

  1. 회원은 회원번호로 구별하며 회원명을 관리합니다. 같은 이름의 회원이 여러 명 있을 수 있습니다.
  2. 상품은 상품번호로 구별합니다. 상품명과 현재 판매 단가를 관리하며, 단가는 원 단위의 0 이상 정수입니다.
  3. 로그인한 회원만 주문할 수 있습니다. 시스템은 주문번호와 주문 회원, 주문 접수 시각을 기록합니다.
  4. 한 주문에는 서로 다른 상품을 1종 이상 담습니다. 같은 상품을 다시 담으면 별도 항목을 만들지 않고 수량을 합칩니다.
  5. 주문 수량은 상품별로 1개 이상 99개 이하인 정수입니다.
  6. 주문 접수 시 수령인명과 배송지를 반드시 입력합니다. 배송 요청사항은 입력하지 않아도 됩니다.
  7. 주문 당시 적용 단가를 기록합니다. 이후 상품의 현재 판매 단가가 바뀌어도 접수된 주문에는 반영하지 않습니다.
  8. 주문 상세 화면에는 항목 금액과 주문 상품 금액 합계를 표시합니다. 이 과제에서는 할인, 세금 계산, 배송비를 다루지 않습니다.
  9. 접수 시각은 한국 표준시를 기준으로 날짜와 시각을 기록합니다.
  10. 운영 담당자는 “최근 주문을 우선 표시하고, 오래된 주문은 별도로 보관한다”고 설명했습니다. ‘최근’, ‘오래된’, ‘별도 보관’의 기준은 아직 정하지 않았습니다.

작성할 내용

  • 요구사항별로 필요한 데이터를 적고, 입력 데이터·시스템 기록·계산 결과로 구분합니다.
  • 엔터티 후보를 묶고, 각 엔터티의 한 행이 뜻하는 바를 한 문장으로 적습니다.
  • 속성별 의미, 단위·허용값, 필수 여부, 값의 출처, 근거 요구사항 번호를 작성합니다.
  • 계산 결과는 계산식과 원본 데이터를 적고, 원본 속성과 구분합니다.
  • 미확정 사항은 질문, 설계에 미치는 영향, 확인 상태를 적습니다.
