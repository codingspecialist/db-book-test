5장. 정규화란?

정규화(normalization)는 데이터의 종속 관계를 기준으로 테이블 구조를 정리하는 과정입니다. 같은 사실을 여러 행에 반복해서 저장하면 삽입·갱신·삭제 이상이 생길 수 있습니다. 정규화는 이러한 문제를 줄입니다. Oracle 문서에서도 정규화의 목적을 중복과 이상 현상을 줄이는 것으로 설명합니다.

앞 장에서는 행을 구별하는 키와 테이블 사이의 관계를 설계했습니다. 이 장에서는 키를 기준으로 어떤 속성을 함께 저장할지 판단합니다. 테이블을 나눈 뒤에도 원래 정보를 정확히 복원할 수 있는지 확인합니다.

1. 중복과 데이터 이상 현상

1.1 삽입·갱신·삭제 이상

주문과 회원, 상품 정보를 하나의 테이블에 저장했다고 가정합니다. 한 행은 주문에 포함된 상품 한 종류를 나타냅니다. 같은 주문에 같은 상품을 두 번 나누어 담지 않는 업무입니다. 따라서 후보키는 (주문번호, 상품번호)입니다.

주문번호회원번호현재 회원명상품번호현재 상품명수량주문단가
700141김서윤P10탁상 조명228000
700141김서윤P20무선 충전기119000
700241김서윤P10탁상 조명126000
700352이도현P30노트북 거치대135000

현재 회원명과 현재 상품명은 각각 회원과 상품의 최신 이름입니다. 주문단가는 해당 주문에서 실제로 적용한 개당 가격입니다. 할인에 따라 같은 상품의 주문단가가 달라질 수 있습니다.

여러 종류의 사실을 한 테이블에 섞으면 데이터를 변경할 때 문제가 생깁니다. 이러한 문제를 이상 현상(anomaly)이라고 합니다.

이상 현상위 테이블에서 생기는 문제
삽입 이상아직 주문되지 않은 상품을 등록하려 해도 주문번호와 회원 정보가 필요합니다.
갱신 이상회원 41의 이름을 바꿀 때 여러 행을 수정해야 합니다. 일부만 바꾸면 현재 회원명이 서로 달라집니다.
삭제 이상주문 7003의 행을 삭제하면 상품 P30의 이름도 함께 사라집니다.

삽입 이상(insert anomaly)은 어떤 사실을 저장하기 위해 관련 없는 다른 사실까지 요구하는 문제입니다. 주문번호가 키의 일부라면 주문이 없는 상품을 이 구조에 그대로 넣을 수 없습니다.

갱신 이상(update anomaly)은 같은 사실이 여러 곳에 있어 변경 내용을 일관되게 반영하기 어려운 문제입니다. 회원명을 한 행에서만 고치면 같은 회원에게 서로 다른 현재 이름이 남습니다.

삭제 이상(delete anomaly)은 어떤 사실을 지우면서 보관해야 할 다른 사실까지 잃는 문제입니다. 주문 내역을 삭제하는 작업이 상품 정보의 삭제로 이어져서는 안 됩니다.

입력과 수정 절차를 주의 깊게 만드는 것만으로는 한계가 있습니다. 회원, 상품, 주문을 각각 독립적으로 관리하도록 저장 구조도 바꾸어야 합니다.

1.2 같은 값과 같은 사실의 구분

정규화는 같은 글자나 숫자를 모두 없애는 작업이 아닙니다. 반복된 값이 무엇을 뜻하는지 확인해야 합니다.

반복되는 값의미판단
여러 주문의 회원번호 41각 주문을 회원 41이 했다는 사실관계를 나타내므로 필요합니다.
여러 행의 현재 회원명 김서윤회원 41의 현재 이름한 곳에서 관리할 사실입니다.
서로 다른 주문의 수량 1각 주문에서 해당 상품을 한 개씩 구매함서로 다른 사실입니다.
여러 주문의 주문단가 28000각 주문에서 적용한 가격숫자가 같아도 별개의 거래 사실입니다.

회원번호를 여러 주문에 저장하는 것은 각 주문의 주문자를 나타냅니다. 반면 현재 회원명을 여러 주문에 복사하면 회원 한 명의 이름을 여러 곳에서 관리하게 됩니다.

상품 가격도 의미를 구분해야 합니다. 현재 판매가격은 상품의 속성일 수 있습니다. 주문단가는 특정 주문에 적용한 가격이므로 주문 항목의 속성입니다. 두 가격이 오늘 같더라도 같은 사실은 아닙니다.

반복된 값을 발견하면 “어떤 대상의 어떤 사실인가?”를 먼저 묻습니다. 한 사실을 바꿀 때 여러 행을 함께 고쳐야 하는지도 확인합니다. 다만 함께 바뀐다는 현상만으로 결론을 내리지는 않습니다. 업무 규칙으로 그 이유를 설명해야 합니다.

2. 함수 종속성과 정규형

2.1 업무 규칙에서 결정자 찾기

함수 종속성(functional dependency)은 어떤 속성의 값이 정해지면 다른 속성의 값도 하나로 정해지는 관계입니다. X → Y로 쓰며 “X가 Y를 결정한다”라고 읽습니다. X를 결정자(determinant)라고 합니다.

앞의 주문 테이블에는 다음 업무 규칙을 적용합니다.

업무 규칙함수 종속성
주문 한 건의 주문자는 한 명입니다.주문번호 → 회원번호
회원 한 명의 현재 이름은 하나입니다.회원번호 → 현재 회원명
상품 하나의 현재 이름은 하나입니다.상품번호 → 현재 상품명
한 주문의 상품별 수량과 적용 단가는 하나씩입니다.(주문번호, 상품번호) → 수량, 주문단가

함수 종속성은 허용되는 모든 데이터에서 성립해야 합니다. 지금 데이터에서 주문번호와 상품번호가 우연히 일대일로 대응할 수는 있습니다. 그래도 주문 하나에 여러 상품을 담을 수 있다면 주문번호 → 상품번호는 성립하지 않습니다.

같은 결정자 값에서 서로 다른 종속 값이 나오면 해당 함수 종속성을 위반합니다. 예를 들어 회원번호 41의 현재 회원명이 한 행에서는 김서윤, 다른 행에서는 김하린일 수 있습니다. 이는 회원번호 → 현재 회원명 규칙에 맞지 않습니다.

반대 방향이 자동으로 성립하지도 않습니다. 동명이인이 있을 수 있으므로 현재 회원명 → 회원번호라고 판단해서는 안 됩니다.

정규화의 조건을 단계별로 정리한 것을 정규형(normal form)이라고 합니다. 정규형은 데이터 몇 건의 모양이 아니라 후보키와 종속 관계를 기준으로 판단합니다.

2.2 제1정규형과 반복 속성 분리

제1정규형(First Normal Form, 1NF)에서는 각 속성이 정해진 값의 범위에서 하나의 원자적인 값을 가집니다. 여기서 도메인(domain)은 속성에 허용되는 값의 범위입니다. 원자적이라는 말은 해당 모델에서 하나의 값으로 다룬다는 뜻입니다.

다음 구조는 상품 여러 개를 목록으로 묶어 저장합니다.

주문번호상품번호 목록수량 목록
7001P10, P202, 1

P20의 수량을 찾으려면 두 문자열을 나눈 뒤 같은 위치의 값끼리 연결해야 합니다. 한쪽 목록에서 항목을 빠뜨리면 상품과 수량의 대응도 어긋납니다.

상품과 수량을 각각 다루어야 하므로 주문 항목을 행으로 나눕니다.

주문번호상품번호수량
7001P102
7001P201

상품번호 대신 상품 ID 목록을 넣어도 목록을 저장한다는 문제는 같습니다. 외래키로 연결할 값도 각 행에 하나씩 저장해야 합니다.

상품번호1, 상품번호2, 상품번호3처럼 반복 컬럼을 두는 방식도 피합니다. 상품을 더 담으려면 테이블 구조를 바꾸어야 합니다. 특정 상품을 찾을 때도 여러 컬럼을 확인해야 합니다. 개수가 달라지는 주문 항목은 필요한 만큼 행을 추가하는 구조로 표현합니다.

다만 번호가 붙은 컬럼이 모두 반복 속성은 아닙니다. 주문일과 결제일처럼 의미가 다른 속성은 별개 컬럼으로 둘 수 있습니다.

원자적인 값을 저장한다고 해서 글자 단위까지 나누라는 뜻도 아닙니다. 전체 이름을 한 값으로 사용한다면 이름 컬럼에 저장할 수 있습니다. 성과 이름을 따로 관리해야 하는지는 서비스의 사용 방식에 따라 판단합니다.

2.3 제2정규형과 부분 함수 종속

제2정규형(Second Normal Form, 2NF)은 제1정규형을 만족하면서, 후보키에 속하지 않는 모든 속성이 모든 후보키에 완전 함수 종속되는 상태입니다.

후보키에 속하는 속성을 주요 속성(prime attribute)이라고 합니다. 어느 후보키에도 속하지 않는 속성은 비주요 속성(non-prime attribute)입니다. 기본키로 선택했는지만 보는 것이 아니라 모든 후보키를 기준으로 구분합니다.

완전 함수 종속(full functional dependency)은 결정자 전체가 있어야 성립하는 종속입니다. 결정자의 일부만으로도 성립하면 부분 함수 종속(partial functional dependency)입니다.

앞의 주문 테이블에서 후보키는 (주문번호, 상품번호)입니다.

속성필요한 결정자후보키와의 관계
회원번호주문번호후보키 일부에 종속됩니다.
현재 회원명주문번호후보키 일부에 종속됩니다.
현재 상품명상품번호후보키 일부에 종속됩니다.
수량주문번호와 상품번호후보키 전체에 종속됩니다.
주문단가주문번호와 상품번호후보키 전체에 종속됩니다.

현재 회원명은 주문번호 → 회원번호 → 현재 회원명으로 결정됩니다. 따라서 주문번호만 알아도 결정되며 상품번호는 필요하지 않습니다.

부분 함수 종속을 분리하면 다음 구조가 됩니다.

테이블속성후보키
주문주문번호, 회원번호, 현재 회원명주문번호
상품상품번호, 현재 상품명상품번호
주문항목주문번호, 상품번호, 수량, 주문단가(주문번호, 상품번호)

주문의 회원 정보는 주문마다 한 번 저장합니다. 상품명은 상품마다 한 번 저장합니다. 주문항목에는 주문과 상품의 조합에 따라 정해지는 수량과 주문단가를 둡니다.

이 단계에서도 주문 테이블에는 회원명이 반복될 수 있습니다. 한 회원이 주문을 여러 번 할 수 있기 때문입니다. 이 문제는 제3정규형에서 다룹니다.

주문항목에 별도의 항목번호를 기본키로 추가해도 종속 관계는 사라지지 않습니다. (주문번호, 상품번호)가 계속 후보키라면 그 조합도 검사해야 합니다. 대리키를 추가하는 것만으로 정규화가 끝나지는 않습니다.

2.4 제3정규형·BCNF와 결정자 조건

제3정규형(Third Normal Form, 3NF)은 제2정규형에서 남을 수 있는 이행 함수 종속 문제를 다룹니다. 이행 함수 종속(transitive functional dependency)은 다른 속성을 거쳐 값이 결정되는 종속입니다.

앞에서 만든 주문 테이블에는 다음 관계가 남아 있습니다.

출발 속성결정되는 속성
주문번호회원번호
회원번호현재 회원명

주문번호로 회원번호를 알고, 회원번호로 현재 회원명을 알 수 있습니다. 회원명은 회원에 관한 사실이므로 다음처럼 분리합니다.

테이블속성후보키
회원회원번호, 현재 회원명회원번호
주문주문번호, 회원번호주문번호
상품상품번호, 현재 상품명상품번호
주문항목주문번호, 상품번호, 수량, 주문단가(주문번호, 상품번호)

회원명을 바꿀 때는 회원 테이블의 한 행만 수정합니다. 주문은 회원번호로 연결하므로 바뀐 현재 회원명을 조회할 수 있습니다.

제3정규형의 정확한 조건은 다음과 같습니다. 모든 비자명한 함수 종속 X → A에서 X가 슈퍼키이거나 A가 주요 속성이어야 합니다.

비자명한 함수 종속(non-trivial functional dependency)은 오른쪽 속성이 왼쪽 속성 집합에 포함되지 않는 종속입니다. 상품번호 → 현재 상품명이 해당합니다. 반면 (주문번호, 상품번호) → 상품번호는 자명한 종속입니다. 왼쪽에 이미 상품번호가 있기 때문입니다.

보이스-코드 정규형(Boyce-Codd Normal Form, BCNF)은 조건이 더 엄격합니다. 모든 비자명한 함수 종속에서 결정자가 슈퍼키여야 합니다. 제3정규형에서 허용하는 “오른쪽이 주요 속성인 경우”도 예외로 두지 않습니다.

차이를 확인하기 위해 공급업체, 상품, 공급담당자의 배정 관계를 생각해 봅시다. 이 사례에서는 다음 규칙만 성립한다고 가정합니다.

공급업체와 상품의 조합마다 담당자를 한 명 배정합니다. 담당자는 한 공급업체에만 소속됩니다. 공급업체는 여러 담당자를 둘 수 있고, 담당자 한 명이 여러 상품을 맡을 수 있습니다.

함수 종속성의미
(공급업체번호, 상품번호) → 담당자번호업체의 상품별 담당자는 한 명입니다.
담당자번호 → 공급업체번호담당자의 소속 업체는 하나입니다.

후보키는 (공급업체번호, 상품번호)와 (담당자번호, 상품번호)입니다. 세 속성이 모두 어느 후보키에든 포함되므로 모두 주요 속성입니다.

담당자번호 → 공급업체번호에서 공급업체번호는 주요 속성입니다. 따라서 제3정규형 조건은 만족합니다. 하지만 담당자번호만으로 상품번호까지 알 수는 없습니다. 담당자번호는 슈퍼키가 아니므로 BCNF는 만족하지 않습니다.

BCNF로 분해하면 다음과 같습니다.

테이블속성
담당자소속담당자번호, 공급업체번호
담당상품담당자번호, 상품번호

담당자의 소속 업체를 한 곳에서 관리할 수 있습니다. 다만 원래의 모든 규칙을 각 테이블에서 따로 검사할 수 있는지는 추가로 확인해야 합니다.

3. 테이블 분해의 검증

3.1 무손실 분해와 종속성 보존

테이블을 작게 나누었다고 올바른 설계가 되는 것은 아닙니다. 원래 정보를 복원할 수 있는지, 원래 업무 규칙을 유지할 수 있는지 확인해야 합니다.

무손실 분해(lossless decomposition)는 분해한 테이블을 조인했을 때 원래의 행 집합을 정확히 복원할 수 있는 분해입니다. 컬럼을 빠뜨리지 않았더라도 원래 없던 조합이 생기면 무손실 분해가 아닙니다.

다음 주문 항목을 보겠습니다.

주문번호상품번호수량
7001P102
7002P101

이 테이블을 (주문번호, 상품번호)와 (상품번호, 수량)으로 나누었다고 가정합니다.

주문번호상품번호

7002P10

주문번호상품번호수량
7001P102
7001P101
7002P102
7002P101

주문 7001의 수량 1과 주문 7002의 수량 2는 원래 없던 조합입니다. 수량이 어느 주문에 속했는지 잃었기 때문입니다.

함수 종속성을 기준으로 두 테이블로 분해할 때는 공통 속성을 확인합니다. 공통 속성이 적어도 한쪽 테이블의 슈퍼키인지 살펴보면 됩니다. 위 분해에서는 공통 속성인 상품번호가 어느 쪽의 슈퍼키도 아닙니다.

반면 (상품번호, 현재 상품명)과 나머지 주문 정보로 분해하면, 공통 속성인 상품번호가 상품 테이블의 키입니다. 상품번호마다 상품명이 하나이므로 원래의 대응을 유지할 수 있습니다.

종속성 보존(dependency preservation)은 분해한 테이블 각각의 종속성만으로 원래의 함수 종속성을 모두 보장할 수 있는 성질입니다. 여러 테이블을 조인해서 검사하지 않아도 된다는 점에서 의미가 있습니다.

앞 절의 담당자 배정을 다시 보겠습니다. BCNF로 나눈 두 테이블에 다음 데이터가 들어갈 수 있습니다.

담당자번호공급업체번호
D1S1
D2S1
담당자번호상품번호
D1P10
D2P10

담당자별 소속은 하나이고, 담당자와 상품의 조합도 중복되지 않습니다. 그러나 조인하면 S1의 P10에 담당자가 두 명 배정됩니다. 원래의 (공급업체번호, 상품번호) → 담당자번호 규칙을 위반합니다.

이 분해는 무손실이지만 모든 함수 종속성을 보존하지는 못합니다. 무손실이라는 말은 규칙에 맞는 원래 데이터를 분해했다가 복원할 수 있다는 뜻입니다. 분해한 테이블에 이후 어떤 데이터를 넣어도 원래 규칙이 자동으로 유지된다는 뜻은 아닙니다.

함수 종속성을 기준으로 제3정규형을 구성하면 무손실과 종속성 보존을 함께 만족하도록 설계할 수 있습니다. BCNF로 분해할 때는 종속성 보존을 잃을 수 있습니다. 정규형 이름만 보고 선택하지 말고, 남은 규칙을 어디서 어떻게 보장할지도 판단해야 합니다.

3.2 제4·제5정규형이 필요한 상황

BCNF까지는 함수 종속성에 초점을 맞춥니다. 여러 값의 조합 때문에 생기는 중복은 다른 종속 관계로 설명해야 할 수 있습니다.

제4정규형(Fourth Normal Form, 4NF)은 서로 독립적인 다중 값의 조합을 다룹니다.

공급업체마다 취급 상품과 지원 배송지역을 관리한다고 가정합니다. 이 업무에서는 업체가 취급하는 모든 상품을 그 업체의 모든 지원 지역에 배송할 수 있습니다.

공급업체번호상품번호배송지역
S1P10서울
S1P10부산
S1P20서울
S1P20부산

S1이 취급하는 상품은 P10과 P20입니다. 배송지역은 서울과 부산입니다. 두 목록이 독립적이어서 모든 조합을 저장합니다.

이 관계를 다치 종속(multivalued dependency)으로 설명합니다. 공급업체번호 ↠ 상품번호처럼 표기합니다. 이 사례에서는 업체별 상품 집합과 배송지역 집합이 서로 독립적이라는 뜻입니다.

한 업체에 상품이 여러 개 있다는 이유만으로 이러한 분해를 적용하지는 않습니다. 다른 속성 집합과의 독립성이 핵심입니다.

제4정규형의 조건은 모든 비자명한 다치 종속의 결정자가 슈퍼키인 것입니다. 여기서 비자명하다는 말은 종속 속성이 결정자에 포함되지 않는다는 뜻입니다. 동시에 두 속성 집합을 합쳐도 테이블의 전체 속성이 되지 않아야 합니다.

위 테이블에는 공급업체번호를 결정자로 하는 비자명한 다치 종속이 있습니다. 공급업체번호만으로는 한 행을 구별할 수 없으므로 제4정규형을 만족하지 않습니다. 다음처럼 분해합니다.

테이블속성
공급상품공급업체번호, 상품번호
공급지역공급업체번호, 배송지역

상품 하나를 추가할 때 배송지역 수만큼 행을 만들 필요가 없습니다.

반대로 P10은 서울에만, P20은 부산에만 배송할 수 있다면 두 목록은 독립적이지 않습니다. 이 경우에는 업체·상품·지역의 조합 자체가 사실이므로 세 속성의 관계를 보존해야 합니다.

제5정규형(Fifth Normal Form, 5NF)은 여러 테이블로 나누었다가 조인하는 관계를 더 일반적으로 다룹니다. 원래 테이블이 여러 부분 테이블의 조인으로 정확히 복원되어야 한다는 조건을 조인 종속성(join dependency)이라고 합니다. 제5정규형에서는 모든 비자명한 조인 종속성이 후보키에서 따라 나와야 합니다.

공급업체·상품·판매점의 납품 관계를 생각해 봅시다. 다음 세 관계가 모두 성립하면 납품 조합도 반드시 허용한다는 업무 규칙이 있을 수 있습니다.

두 대상의 관계뜻
공급업체와 상품업체가 해당 상품을 공급할 수 있습니다.
공급업체와 판매점업체가 해당 판매점과 거래할 수 있습니다.
상품과 판매점판매점이 해당 상품을 취급할 수 있습니다.

이 규칙이 실제로 성립한다면 세 관계를 각각 저장하고 조인하여 납품 가능 조합을 구할 수 있습니다. 세 속성을 매번 한 행에 함께 저장할 필요가 없습니다.

하지만 세 쌍이 각각 허용되어도 특정 세 대상의 조합은 금지될 수 있습니다. 예를 들어 업체 S1이 상품 P10을 공급하고 판매점 T1과 거래할 수는 있습니다. 그래도 P10을 T1에 납품하는 계약은 없을 수 있습니다. 이런 업무에서 세 관계만 저장하면 존재하지 않는 납품 조합을 만들어 냅니다.

제4·제5정규형은 여러 값이나 세 대상이 등장한다는 이유만으로 적용하지 않습니다. 값들의 독립성과 조합을 허용하는 업무 규칙이 확인될 때 적용합니다.

3.3 분해한 테이블로 원래 정보 복원하기

주문 테이블을 회원, 주문, 상품, 주문항목으로 분해한 결과를 SQL로 확인합니다. 실습은 SQL Developer에서 실행합니다.

예제는 공통 테이블 식인 WITH 절로 원본과 분해 결과를 만듭니다. 실제 테이블을 생성하지 않으므로 앞 장의 실습 객체가 없어도 실행할 수 있습니다.

원본과 복원 결과는 두 방향으로 비교해야 합니다. 원본에서 복원 결과를 빼면 누락된 행을 찾습니다. 복원 결과에서 원본을 빼면 새로 생겼거나 값이 달라진 행을 찾습니다.

예제 5-1 — 정규화 전후의 주문 정보 비교하기

파일명: ch05_restore_orders.sql

WITH
draft (
    order_id,
    member_id,
    member_name,
    product_id,
    product_name,
    quantity,
    order_price
) AS (
    SELECT 7001, 41, '김서윤', 'P10', '탁상 조명', 2, 28000
    FROM dual
    UNION ALL
    SELECT 7001, 41, '김서윤', 'P20', '무선 충전기', 1, 19000
    FROM dual
    UNION ALL
    SELECT 7002, 41, '김서윤', 'P10', '탁상 조명', 1, 26000
    FROM dual
    UNION ALL
    SELECT 7003, 52, '이도현', 'P30', '노트북 거치대', 1, 35000
    FROM dual
),
members AS (
    SELECT DISTINCT member_id, member_name
    FROM draft
),
orders AS (
    SELECT DISTINCT order_id, member_id
    FROM draft
),
products AS (
    SELECT DISTINCT product_id, product_name
    FROM draft
),
order_items AS (
    SELECT order_id, product_id, quantity, order_price
    FROM draft
),
restored AS (
    SELECT o.order_id,
           m.member_id,
           m.member_name,
           p.product_id,
           p.product_name,
           i.quantity,
           i.order_price
    FROM orders o
    JOIN members m
      ON m.member_id = o.member_id
    JOIN order_items i
      ON i.order_id = o.order_id
    JOIN products p
      ON p.product_id = i.product_id
),
original_only AS (
    SELECT order_id, member_id, member_name,
           product_id, product_name, quantity, order_price
    FROM draft
    MINUS
    SELECT order_id, member_id, member_name,
           product_id, product_name, quantity, order_price
    FROM restored
),
restored_only AS (
    SELECT order_id, member_id, member_name,
           product_id, product_name, quantity, order_price
    FROM restored
    MINUS
    SELECT order_id, member_id, member_name,
           product_id, product_name, quantity, order_price
    FROM draft
)
SELECT (SELECT COUNT(*) FROM draft) AS original_rows,
       (SELECT COUNT(*) FROM restored) AS restored_rows,
       (SELECT COUNT(*) FROM original_only) AS original_only,
       (SELECT COUNT(*) FROM restored_only) AS restored_only
FROM dual;

양방향 차이가 모두 0이므로 이 데이터에서는 원본과 복원 결과의 행 집합이 같습니다. 전체 행 수도 같아 조인으로 행이 늘거나 줄지 않았습니다.

MINUS는 집합 차이를 구하므로 중복 행의 개수 차이는 구분하지 않습니다. 일반적인 SQL 결과를 비교할 때는 키별 중복이나 동일 행의 출현 횟수도 확인해야 합니다. 이 예제에서는 원본의 후보키가 중복되지 않는지 함께 확인합니다. 조인 상대에도 키마다 행이 하나씩 있는지 확인합니다.

DISTINCT가 잘못된 종속 관계를 고쳐 주지는 않습니다. 같은 회원번호에 서로 다른 현재 회원명이 들어 있으면 회원 테이블에 두 행이 남습니다. 그러면 조인 결과가 늘어날 수 있습니다. 실제 데이터를 분해할 때는 원래 규칙을 위반한 행부터 찾아 정리해야 합니다.

예제 데이터가 복원된다는 사실만으로 모든 데이터에서 무손실임을 증명하지는 못합니다. 업무 규칙과 키로 분해의 타당성을 판단합니다. SQL 비교로 실제 데이터에서도 그 판단이 맞는지 확인합니다.

분해 후에는 독립적인 사실을 따로 저장할 수 있는지도 점검합니다. 아직 주문이 없는 상품을 상품 테이블에 등록할 수 있어야 합니다. 주문항목을 삭제해도 상품과 회원 정보는 남아야 합니다. 새로 등록한 미주문 상품이 주문 내역 조인에 나오지 않는 것은 정상입니다.

  2. 함수 종속성을 업무 문장과 함께 적습니다. 회원·상품·공급업체의 현재 이름은 각각 번호로 결정됩니다.
  3. 삽입·갱신·삭제 이상을 하나씩 설명합니다. 어떤 사실을 저장하거나 잃는지 구체적으로 적습니다.
  4. 부분 함수 종속을 분리하여 제2정규형 구조를 작성합니다.
  5. 이행 함수 종속을 분리하여 제3정규형 구조를 작성합니다. 각 테이블의 속성, 기본키, 외래키를 표시합니다.
  6. draw.io로 분해 결과를 그립니다. 각 테이블이 관리하는 사실을 한 문장으로 적습니다.
  7. 분해한 데이터를 조인하여 원본을 복원합니다. 원본과 복원 결과를 양방향으로 비교합니다.

추가 검토

공급업체가 여러 배송지역을 지원한다고 가정합니다. “공급업체의 모든 상품을 모든 지원 지역에 배송할 수 있다”는 규칙이 있을 때와 상품별 배송지역이 다를 때를 비교합니다. 두 경우에 같은 테이블 분해를 적용할 수 있는지 이유를 적습니다.
