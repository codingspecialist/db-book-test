22장. 공통코드 설계란?

1. 공통코드와 업무 엔터티의 구분

1.1 고정 허용값·운영 코드·독립 업무 데이터

공통코드(common code)는 여러 업무에서 같은 의미로 쓰는 분류값을 코드와 표시명으로 관리하는 방식입니다. 주문에는 PAID를 저장하고, 화면에는 표시명인 ‘결제 완료’를 보여 주는 식입니다.

반복해서 나타나는 문자열을 모두 공통코드로 바꾸지는 않습니다. 두 회원이 취소 사유에 ‘배송이 늦어서’라고 적었더라도 각자 입력한 문장입니다. 한 회원의 문장을 수정할 때 다른 회원의 문장까지 바뀌어서는 안 됩니다. 반면 운영자가 제공한 취소 사유 목록에서 선택하게 한다면 코드로 관리할 수 있습니다.

값을 어디에 저장할지는 변경 방식과 업무상 역할로 판단합니다.

구분판단 기준예적합한 관리 방식
고정 허용값값의 종류가 적고 프로그램 규칙과 함께 바뀜사용 여부 Y, NCHECK 제약
운영 코드운영 중 항목·표시명·정렬 순서를 관리함취소 사유코드 테이블
독립 업무 데이터자체 속성과 관계, 업무 처리가 있음배송사, 물류센터별도 업무 엔터티

배송사는 코드와 이름만 있을 때 코드 목록처럼 보입니다. 그러나 계약번호, 배송 가능 지역, 정산 조건까지 관리한다면 독립 업무 엔터티로 보는 편이 적절합니다. 표시할 이름이 있다는 이유만으로 통합 코드 테이블에 넣으면 이러한 속성을 담기 어려워집니다.

주문 상태는 운영 코드로 관리하더라도 값을 신중하게 추가해야 합니다. REFUNDED를 코드 목록에 등록했다고 환불 처리가 구현되지는 않습니다. 상태를 해석하는 프로그램과 업무 규칙도 함께 바뀌어야 합니다.

1.2 CHECK 제약·개별 코드 테이블·통합 코드 테이블

여러 업무에서 공통으로 쓰는 분류값은 관리 방법에 따라 다음과 같은 차이가 있습니다.

방법장점주의할 점
CHECK 제약허용값을 테이블에서 직접 제한함허용값 변경에 DDL이 필요함
개별 코드 테이블업무별 속성과 관계를 명확하게 표현함코드 종류마다 테이블이 생김
통합 코드 테이블공통 구조와 관리 화면을 재사용하기 좋음코드 그룹까지 검증해야 함

CHECK 제약은 사용 여부처럼 고정된 값에 적합합니다.

코드 조각

SQL
1 2
use_yn CHAR(1) DEFAULT 'Y' NOT NULL
    CHECK (use_yn IN ('Y', 'N'))

개별 코드 테이블을 사용하면 주문 상태는 order_status_code, 취소 사유는 cancel_reason_code에 저장합니다. 주문 상태 컬럼이 order_status_code를 참조하므로 참조 관계만으로 코드의 종류가 분명해집니다.

통합 코드 테이블은 여러 종류의 코드를 한 테이블에 모읍니다. 이때 ORDER_STATUS, CANCEL_REASON과 같은 코드 그룹(code group)으로 종류를 구별합니다. 코드값은 그룹 안에서 유일하게 관리합니다.

통합 방식은 구조가 비슷한 코드 목록에 적합합니다. 특정 그룹만을 위한 컬럼이 계속 늘어난다면 별도 테이블로 분리할지 검토합니다. 통합 코드 테이블의 행 수를 줄이는 일보다 업무 규칙을 명확하게 표현하는 일이 우선입니다.

2. 코드 그룹과 코드의 구조

2.1 그룹·코드·표시명·정렬 순서

통합 코드 테이블의 한 행은 ‘특정 그룹에 속한 코드 하나’를 뜻합니다. 그룹 자체의 이름은 그룹 테이블에, 각 코드의 정보는 코드 테이블에 둡니다.

그룹코드표시명정렬 순서
ORDER_STATUSCREATED주문 접수10
ORDER_STATUSPAID결제 완료20
CANCEL_REASONCHANGE_MIND구매 의사 변경10
CANCEL_REASONOUT_OF_STOCK재고 부족20

코드는 프로그램이 참조할 식별값입니다. 표시명은 사용자에게 보여 주는 문구입니다. 표시명을 바꾸더라도 코드가 유지되면 저장된 업무 데이터의 참조 관계는 유지됩니다.

정렬 순서는 코드값과 분리합니다. 코드의 사전순이 화면의 업무 순서와 일치한다는 보장이 없기 때문입니다. 정렬 순서가 같을 때도 결과가 일정하도록 코드값을 두 번째 정렬 기준으로 사용할 수 있습니다.

2.2 복합키와 외래키로 코드 그룹 검증

통합 코드 테이블을 참조할 때는 코드의 존재와 소속 그룹을 함께 검증해야 합니다. 주문 상태 컬럼에 취소 사유 코드가 들어가면 코드 자체가 존재하더라도 잘못된 데이터입니다.

이를 막으려면 주문에 그룹과 코드값을 함께 두고 복합 외래키를 만듭니다. 그룹 컬럼에는 CHECK 제약을 걸어 주문 상태 그룹만 허용합니다.

그룹 컬럼의 기본값만으로는 충분하지 않습니다. 기본값은 컬럼을 생략했을 때 값을 채울 뿐입니다. 다른 그룹을 직접 입력하는 일은 막지 못합니다. CHECK 제약이 그룹을 고정하고, 복합 외래키가 그 그룹 안에 코드가 있는지 검증합니다. 두 컬럼에 NOT NULL을 둔 이유도 필수 참조를 보장하기 위해서입니다.

코드 테이블에 별도 대리키를 두더라도 그룹 검증 문제는 남습니다. 대리키만 참조하면 코드의 존재는 확인하지만 주문 상태인지는 보장하지 못합니다. 개별 코드 테이블을 쓰거나, 그룹을 포함한 참조 구조로 소속을 검증해야 합니다.

Oracle의 외래키와 CHECK 제약이 동작하는 기준은 제약조건 문서에서 확인할 수 있습니다.

2.3 사용 여부·적용 기간·다국어 표시

코드가 존재한다는 사실과 신규 업무에서 선택할 수 있다는 사실은 다릅니다. 과거 주문에서 사용한 코드는 남겨 두되, 신규 주문에는 선택하지 못하게 할 수 있습니다.

이 장에서는 사용 여부와 적용 기간의 의미를 다음과 같이 정합니다.

항목의미
use_yn = 'Y'운영자가 신규 선택을 허용함
valid_from선택할 수 있는 시작 시각
valid_to선택할 수 없게 되는 종료 시각
valid_to IS NULL종료 시각을 정하지 않음

선택 가능 여부는 업무에서 정한 기준 시각으로 판단합니다. 예제에서는 DATE 컬럼에 업무 기준 시간대의 시각을 저장한다고 가정합니다.

코드 조각

SQL
1 2 3 4 5 6 7
SELECT code_value, display_name
FROM ch22_common_code
WHERE group_code = 'CANCEL_REASON'
  AND use_yn = 'Y'
  AND valid_from <= :selection_time
  AND (valid_to IS NULL OR :selection_time < valid_to)
ORDER BY sort_order, code_value;

종료 시각은 포함하지 않습니다. 예를 들어 종료 시각이 11월 1일 0시라면 그 시각부터 선택 목록에서 제외됩니다.

외래키는 사용 여부와 적용 기간까지 검사하지 않습니다. 신규 저장 시에는 서버에서도 선택 가능한 코드인지 검증해야 합니다. 화면에서 목록을 제한하는 것만으로는 직접 보낸 요청이나 오래 열어 둔 화면의 입력을 막을 수 없습니다.

코드 사용 중지와 업무 데이터 저장이 동시에 일어날 때의 기준도 정해야 합니다. 저장 순간까지 선택 가능해야 한다면 코드 확인과 저장을 같은 트랜잭션에 묶습니다. 필요한 경우 코드 행 잠금 등을 사용해 사용 중지 작업과 저장 순서를 조정합니다.

과거 주문을 조회할 때는 신규 선택 조건을 그대로 적용하지 않습니다. use_yn = 'Y'를 붙여 조인하면 사용 중지한 코드의 표시명을 읽지 못하거나 주문 자체가 결과에서 빠질 수 있습니다.

다국어 표시가 필요하면 코드 식별값과 번역 문구를 분리합니다. 번역 테이블의 한 행은 ‘코드 하나의 특정 언어 표시명 하나’입니다.

       COALESCE(t.display_name, c.display_name) AS display_name
FROM ch22_common_code c
LEFT JOIN ch22_code_text t
  ON t.group_code = c.group_code
 AND t.code_value = c.code_value
 AND t.language_tag = 'en'
WHERE c.group_code = 'ORDER_STATUS'
ORDER BY c.sort_order, c.code_value;

언어 태그의 표기와 대소문자도 통일합니다. en과 EN을 서로 다른 값으로 등록하지 않도록 입력 규칙을 정해야 합니다. 외부에 전달하는 값은 번역 문구가 아니라 안정된 코드값을 사용합니다.

3. 코드 변경과 운영

3.1 의미 변경·폐기·재사용 정책

표시 문구를 다듬는 일과 코드의 의미를 바꾸는 일은 구별해야 합니다. 같은 코드로 저장된 과거 데이터도 그 의미를 공유하기 때문입니다.

변경 요청처리 기준
‘결제완료’를 ‘결제 완료’로 수정의미가 같다면 표시명 수정
‘결제 완료’를 ‘배송 완료’ 의미로 변경새 코드 생성
취소 사유를 신규 선택에서 제외사용 중지 또는 적용 종료
폐기한 코드값을 다른 의미로 사용재사용 금지
두 코드를 하나로 통합과거 코드 보존과 데이터 전환 정책 검토

코드값을 재사용하면 과거 기록의 해석이 달라집니다. 과거 주문에 저장된 OTHER가 당시에는 ‘기타 사유’였다고 가정합니다. 같은 코드를 새로 ‘판매자 요청’이라는 뜻으로 쓰면 주문 데이터만으로 원래 의미를 구별할 수 없습니다.

참조 중인 코드는 행을 삭제하기보다 신규 선택을 막는 방식으로 폐기하는 편이 적절합니다. 예제의 외래키도 참조 중인 코드의 삭제를 막습니다. 아직 사용하지 않은 오등록 코드라면 참조 여부와 배포 상태를 확인한 뒤 삭제할 수 있습니다.

프로그램 변경 없이 코드를 추가할 수 있는 범위도 정합니다. 취소 사유의 단순 분류 항목은 운영자가 추가할 수 있어도, 주문 상태처럼 프로그램 분기에 쓰는 코드는 개발·배포 절차와 연결해야 합니다.

운영 기준에는 변경 권한과 배포 방법도 포함합니다. 애플리케이션이 코드 목록을 캐시에 보관한다면 사용 중지 후에도 이전 목록이 보일 수 있습니다. 캐시 갱신 시점과 서버 검증 기준을 함께 정해야 합니다.

3.2 과거 기록의 코드명과 현재 표시명

주문에 코드값만 저장하고 공통코드 테이블을 조인하면 현재 표시명을 보여 줍니다. 표시명을 수정한 뒤 과거 주문을 다시 조회해도 새 문구가 나타납니다.

이 동작이 적절한지는 화면의 목적에 따라 다릅니다.

조회 목적표시명 정책
운영 화면에서 현재 용어로 주문 분류현재 표시명 조회
고객에게 발급했던 문서를 그대로 재현발급 당시 표시명 보관
특정 시점에 유효했던 분류명 조회시점별 코드명 관리 검토

당시 문구를 보관해야 한다면 코드값과 별도로 표시명 사본을 저장할 수 있습니다. 코드값은 분류와 집계에, 표시명 사본은 당시 문서 재현에 사용합니다. 같은 문구를 중복 저장하더라도 보관 목적이 다릅니다.

4. 연습문제 — 주문 상태와 취소 사유 코드 설계

주문 서비스에서 주문 상태와 취소 사유를 관리합니다. 다음 요구사항을 읽고 코드 구조와 검증 규칙을 작성합니다.

요구사항

  1. 주문 상태는 ‘주문 접수’, ‘결제 완료’, ‘배송 중’, ‘취소 완료’입니다.
  2. 취소 사유는 운영자가 추가하고 표시 순서를 바꿀 수 있습니다.
  3. 취소 사유에는 한국어와 영어 표시명을 제공합니다.
  4. 사용 중지한 취소 사유는 신규 선택 목록에서 제외합니다.
  5. 과거 주문에 기록된 취소 사유는 사용 중지 후에도 조회되어야 합니다.
  6. 취소 완료 주문에는 취소 사유가 필수입니다. 다른 상태에서는 취소 사유를 저장하지 않습니다.
  7. 고객이 직접 입력하는 상세 설명은 선택한 취소 사유와 별도로 저장합니다.
  8. 취소 확인서에는 발급 당시 취소 사유 문구를 보관합니다.
  9. 폐기한 코드값은 다른 의미로 재사용하지 않습니다.

작성할 내용

  1. 주문 상태와 취소 사유에 사용할 관리 방식을 선택하고 이유를 적습니다.
  2. draw.io로 코드·주문·번역 데이터의 관계를 작성합니다.
  3. 컬럼별 의미, 허용값, 필수 여부를 데이터 사전에 기록합니다.
  4. 코드 그룹 오류와 존재하지 않는 코드를 거부하는 DDL을 작성합니다.
  5. 신규 선택 목록과 과거 주문 조회 SQL을 각각 작성합니다.
  6. 사용 중지 코드의 신규 입력을 검사할 위치와 동시 변경 시 처리 기준을 적습니다.
  7. 표시명 수정·코드 폐기·신규 코드 추가의 운영 절차를 작성합니다.

완료 조건

  • 주문 상태 자리에 취소 사유 코드를 입력할 수 없습니다.
  • 취소 사유가 선택 사항이어도 코드 그룹 검증을 우회할 수 없습니다.
  • 취소 완료 여부와 취소 사유 입력 여부가 일치합니다.
  • 신규 선택 목록은 사용 여부·적용 기간·정렬 순서를 반영합니다.
  • 폐기한 코드를 참조하는 과거 주문도 빠짐없이 조회됩니다.
  • 현재 표시명을 수정해도 발급 당시 문구는 유지됩니다.
  • 자유 입력 상세 설명을 공통코드로 묶지 않습니다.
